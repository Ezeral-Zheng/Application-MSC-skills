# Skill Studio 流程设计原型

本原型验证：顾问是否能先理解 skill 的输入、产物与规则，再按申请方向调整叠加规则，并组合可交给 Agent 的方案。

当前需求优先级已由用户确认：看懂 skills、按方向调整规则并拼接流程。还未选定界面形式；通过 `?variant=A/B/C` 比较节点画布、规则工作表与分步向导，三者共享当前方案。

启动命令（从 Vault 根目录运行）：

```bash
python3 Application_System/tools/skill-studio-prototype/serve.py
```

访问 `http://127.0.0.1:8765/`。服务只监听本机，实时只读读取 `Application_System/skills/*/SKILL.md`。浏览器配置在内存中，刷新会恢复默认；可以导出/导入 JSON 保留四个申请方向的叠加规则，并下载或复制 Markdown 执行提示。原型不写入原始 skill 或学生目录，也不连接模型执行。

能够验证：理解节点职责、添加与排序、同一节点按方向配置、查看基础规则与完整 skill、发现缺少关键阶段或明显顺序错误、通过模拟 Pass/Revise/Blocked 理解审查返回。

当前边界：线性画布展示阶段，不是任意有向图执行器；C/P/S 循环由原有总控流程承接，步骤演练不会产生候选稿或审查结论。静态检查不能证明整个流程可执行。现有部分 skill 自带编排，需要真实执行器把“阶段展示”与“组合 skill 调用”分开，以避免重复写作与重复审查。

落地架构建议：

1. 保留 `SKILL.md` 为基线规则，增加人工维护的节点输入/输出、配置字段及方向覆盖层；不试图把全部自由文本自动转换为可靠执行逻辑。
2. 流程方案保存目标、方向、节点连接、条件与允许的规则覆盖，导出时固定所用 skill 版本。
3. 执行器通过总控 Agent 调用基础 skills，支持全新隔离审稿与修改 worker、状态/轮次持久化、版本预留、失败恢复；执行日志与学生交付分开。
4. 覆盖层先产生可评审差异，再应用到指定方向或流程；学生个体事实不写进通用 skill。

后续根据用户选择，吸收选中布局并移除其余变体；升级为生产系统时重新实现输入验证、版本管理、写回与执行部分。
