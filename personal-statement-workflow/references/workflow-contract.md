# Workflow Contract

## Inputs and precedence

Required inputs are student identity, target school/programme, and enough traceable basic, personalization, course, and experience material to support a safe narrative. Prefer, in order: the user's current explicit facts; traceable confirmed Markdown; preference memory for style only; reasonable inferences for abstract framing only. Pending confirmations are never formal facts.

Read relevant attachment `.md` files when source material names an attachment. Do not redownload or reinterpret binary attachments during drafting if a standardized Markdown source exists.

## Narrative design contract

Before prose, record for the target:

- one-sentence proposition containing existing capability, unresolved problem, and why the target degree is necessary;
- the causal path from concrete problem to learning need and programme choice;
- each evidence item's sole duty: trigger, decision, counterexample, constraint, capability proof, capability boundary, or career validation;
- required, optional, and explicitly discarded evidence;
- capability gap, career direction, programme-fit resources, and structure signature;
- differences from adjacent targets in at least two of: causal entry, evidence selection, evidence duty, location of capability gap, career derivation, or ending function.

When reusing an experience, preserve the minimum immutable fact core but change at least three of: selected passage, core question, action focus, constraint, and capability conclusion. If no genuine semantic delta exists, discard it or compress it to one background sentence.

## Draft contract

The formal PS is one Markdown file with English first and Chinese second. Both are continuous prose and fact-consistent; the Chinese is a natural counterpart, not a second fact set. Cover the applicant's academic choice, relevant evidence, career direction, and master's/programme choice, but let the proposition determine order and paragraph count. Usually expand only two or three programme resources, each tied to an experience, a capability gap, and a future use. Do not fabricate programme details when the source is insufficient.

## Factual/compliance gate

Check source traceability, student/material identity, timeline, bilingual consistency, target-programme claims, placeholders, template/reference residue, Markdown format, and reserved-version naming. `application-review` is a factual and compliance gate; it does not replace independent content review. Use `Pass`, `Needs Fix`, or `Blocked`. Pure rhetorical similarity or weak persuasion belongs to content review, not factual auto-repair.

## Content review contract

Each `single-draft` reviewer is a new subagent that sees only the current candidate, target requirements, minimum programme summary, the review skill/criteria, and the current `Cn`. It must not see the writer's context, previous drafts, scores, reports, student history, or complete source vault.

Each issue should include: stable ID, dimension, priority, shortest location/evidence, reader impact, concrete action, fact boundary, content to preserve, confirmation need, and acceptance criterion. The controller automatically accepts Must Fix, selectively accepts high-value Should Fix, and does not apply Optional or Needs Confirmation items without a decision.

The seven-dimension gate passes only at average `>= 8.5`, with no P0/Must Fix, no actionable P1/Should Fix, and no course-listing failure. `C1`–`C5` is a shared content-review counter for single-draft and portfolio review; it must never be reset.

## Isolated revision contract

The revision worker is a different fresh subagent. It receives only the current `Rn`, sanitized accepted issue handoff, minimum confirmed facts with source paths, output requirements, and temporary output paths. It must not receive full reports, scores, old drafts, memory/history, unaccepted suggestions, or other student files. It returns only the next `Rn` and an issue disposition table. The controller owns versioning, review calls, formal publishing, and memory updates.

## Portfolio review contract

When other formal PSs exist, the portfolio reviewer sees only the current candidate, the narrative matrix, the latest formal PS for each other target, and the similarity-tool report. It checks proposition, causal entry, evidence duty, repeated structure, repeated full fact/action/reflection packages, and whether the target differs materially. A substantive portfolio fix must use a sanitized minimum-difference packet and return through factual review plus a fresh single-draft review.

## Publishing contract

Reserve one `Vn` at task start. Keep all `Rn`, `Cn`, reports, handoffs, fact packets, and disposition tables in the same temporary task directory. Publish exactly one Markdown `Vn` only after all gates pass; never overwrite an existing formal version. After publication, write the final factual/content reports, revision summary where applicable, review memory, preference updates only for stable student-style observations, task-board update, and version-index refresh. A failed task does not consume a formal version.
